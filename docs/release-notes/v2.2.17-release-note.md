【升级影响 · 本次为新增功能与两项既有缺陷修复，已有单据数据与计算口径一律不变，升级前请知悉】本次相对 v2.2.16 新增库存盘点单、不良品处置单、统一检验单（IQC / IPQC / OQC / FAI）与检验台账、返工单及四类基础台账（物料替代 / 工程变更 ECN / 设备停机 / 供应商评分），把整批报工终审与检验依据打通，并修复 CRM 商机查询报错、质检配置写操作不落库两项既有缺陷。对照「旧数据和旧集成在不做任何操作的情况下会不会得到不同结果」这条判据，结论是：不会。唯一需要在升级前知悉的行为变化，是主动执行「质检模板 / 缺陷代码」配置写操作时结果会与升级前不同，已单列在【哪类会变】。以下按「哪类会变 / 哪类不变 / 历史数据怎么办 / 需要你做什么」逐项说明，便于快速判断自己是否受影响。

【哪类会变】仅一处，且只在主动执行配置写操作时发生：质检模板与缺陷代码的创建、编辑、删除共 6 个端点。v2.2.16 及更早，这些端点返回 200 并回显 id，但请求结束即回滚、数据没有进表；本次修复后真实落库（删除为软删 is_active=False，列表不再显示该行）。豁免条件：从未使用过这些配置写端点的实例，升级前后表现一致，可直接排除自查。历史「以为保存成功、实际未写入」的配置不会自动补，需重新保存一次；升级过程不回填、不重算任何既有配置行。除此之外，本次不含任何改写存量单据、既有金额口径或既有必填入参的变更，没有需要逐单核对的历史数据。

【哪类不变 · 可据此直接排除自查】① 已有单据金额与计算口径不变：报价单税额（按行税率合计、tax_rate 仅为兜底税率）、工资、库存结存、盘点入账等既有算法一行未改；② 已有单据数据不重算、不回填：本次 4 个迁移（0016~0019）只做加法，新增 5 张台账表初始为空、inspection_orders 新增两列可空，升级过程不 UPDATE 任何存量行；③ 已有接口调用方式不变：POST /admin/production/reports/{id}/qc-approve 不传 inspection_id 时，审核流水、工资明细、追溯码、通知与状态流转与 v2.2.16 逐字一致，响应体只多一个可忽略的 inspection_code 键；④ 业务主档不动：新台账只登记，不自动改 BOM、设备 / 供应商主档、库存、reports.good_qty，也不推进采购 / 发货 / 工单 / 报工状态；⑤ 检验闸门仍不强制：是否必须挂检验单由客户按数据决定，系统不代业务拍板；⑥ CRM 商机只读查询：列表 / 看板等 4 个 GET 从 500 恢复为 200，只是错误消失，不写入、不改写任何已有商机数据，也不改变查询口径。

【历史数据如何处理】不自动重算、不自动回填。若需要把历史单据纳入新台账，按各自端点逐单操作。例：历史处置单补返工单用 POST /admin/production/dispositions/{id}/generate-reworks，该端点幂等，重复调用不会生成重复工单；一条「退回工序」明细始终只对应一张返工单。质检配置的历史缺口同样不自动补，按上一段重新保存即可。

【升级后需要你做的一件事】本次新增 11 个权限点（rework / substitute / ecn / downtime / supplier_score 的 view 与 manage 等）。内置角色由启动逻辑自动补齐，但客户自建角色不会自动获得这些权限——新菜单可能出现「看得见、点不动」。请在后台「角色管理」按岗位逐个授权：PUT /api/admin/system/roles/{id}/permissions，注意该接口是全量替换，须先读出该角色全量权限再合并回写，直接提交会清空原有权限。

【条件性提示 · 仅针对跑过中间代码的实例】若你的实例曾通过直接部署或「快路」更新跑过 0017 / 0018 之后、但未打 tag 的代码，本次起「批准处置单」会额外生成返工单，升级前已批准的处置单不会自动补，请用上面的幂等端点逐单补齐；同时 /admin/production/inspections/source-options 的 OQC / FAI 分支返回键与 label 文案相对中间版本有扩展，若有自定义前端依赖该返回体请核对。从 v2.2.16 正式升级的客户不涉及这两条，可直接跳过。

统一检验单与检验台账（0018_inspection）：新增 IQC / IPQC / OQC / FAI 四类检验单、模板快照、判定与关闭状态机（用 closed_at 保留 passed / failed 结论，不覆盖判定结果），检验记录台账可按条件查询、查看明细与导出；静态路由统一注册在 /{id} 之前，避免被解析成 id 返回 422。

质量主线联动与基础台账（0019_basics）：整批报工终审新增可选 inspection_id，传了才校验「IPQC + 判定合格 + 挂在本报工上」并把检验单号写入审核流水 reason；OQC 从发货单带出客户 / 产品 / 数量、FAI 从任务带出工序 / 产品 / 计划数，新增来源汇总与按报工查询端点；处置批准按「一条退回工序明细一张返工单」幂等生成，并完成开工 / 完成 / 作废状态机与良品数回流；新增物料替代、工程变更 ECN、设备停机、供应商评分四类台账，供应商评分总分按质量 40% / 交期 30% / 价格 20% / 服务 10% 由系统计算、停机时长只由起止时间算，均不接收前端传值。同步新增 11 个权限点、RW / ECN / DT 三种单号规则、返工单与基础台账两个管理页面及中 / 英 / 韩三语文案。

缺陷修复（随本版一起发布）：① CRM 商机列表 / 看板等 4 个 GET 返回 500，根因是独立版单租户兼容层 tenant_setting.get_setting / upsert_setting 不接受 tenant_id= 关键字，SaaS 时期遗留的调用方式触发 TypeError。修法是在兼容层加 keyword-only tenant_id 只吸收不用，不逐端点打补丁；修复后 4 个端点真实 HTTP 均返回 code=200。② 质检模板与缺陷代码 6 个写端点返回 200 却不落库，根因是 get_db() 只 yield + close（autocommit=False），crud/quality.py 全程只 flush，API 层没有显式提交，请求结束即回滚。修法是 6 个写端点统一补 db.commit()，创建 / 更新先序列化再提交以避开 expire_on_commit 后的属性重载；删除保持既有软删语义。新增回归用 spy session 统计 commit() 调用次数——同一事务内 SELECT 分不出 flush 和 commit，这是唯一能钉住该缺陷的写法。
