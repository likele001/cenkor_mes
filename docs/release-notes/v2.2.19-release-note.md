【升级影响 · 本次为宿主核心 Celery / 扩展加载机制缺陷修复，不含数据库迁移、不含后端接口变更、不含任何金额与计价口径调整，存量单据与集成方式一律不变；但有一类实例的行为会实质改变——装了商业扩展的实例，worker 侧此前一直失败的周期任务在升级后会真正开始执行，首次投递可能补跑积压待办，请知悉后再升级】本次相对 v2.2.18 改动 3 个提交、共 4 个文件：backend/app/celery_app.py、backend/app/extension_host/loader.py、backend/tests/test_extension_core_table_guard.py（新增）、backend/tests/test_basics.py。修复的是宿主从扩展机制上线起就存在的两个叠加缺陷：worker 同时挂载 worker_init 与 worker_process_init，导致同一进程内两次调用 import_extension_modules()；而每次加载扩展前的 purge_extension_modules() 里，_detach_extension_tables() 会对 Table 对象强制把归属者记成「当前扩展模块名」。当某个扩展的模块里出现核心表对象（典型写法 from app.models.user import user_roles），这张核心表就会被当作扩展自有表从共享 metadata 中摘除，随后 SQLAlchemy 解析 Role.users 这条 relationship("User", secondary="user_roles") 时找不到名字，抛 InvalidRequestError 并进入重试。对照「旧数据和旧集成在不做任何操作的情况下会不会得到不同结果」这条判据，结论是：对零扩展实例不变；对装了扩展的实例会变，且变化方向是「把本来就该跑的任务修回能跑」。以下按「哪类会变 / 哪类不变 / 历史数据怎么办 / 需要你做什么」逐项说明。

【哪类会变】① 装了商业扩展、且该扩展模块内引用过核心表对象的实例：worker 侧此前报 Received unregistered task 或 failed to locate a name 'user_roles' 的周期任务，升级后能正常执行。② 同一类实例上，宿主自身的周期任务 production.automation.pipeline 也会连带失败（因为它同样要解析 Role.users 关系），升级后恢复成功——这条不是扩展的问题，是被扩展连坐的宿主核心任务。③ 因此升级后第一次 beat 周期，自动化流水线与扩展周期任务可能一次性处理掉此前积压的待办（到点未扫的巡检计划、到期未推进的工单自动化），会产生新的业务记录与站内通知。这属于「本来就该发生但一直被阻塞」的正常执行，不是重复计算，也不是数据被改写。④ 数据库表结构与数据一行不动，摘表只发生在进程内存里的 SQLAlchemy metadata，不涉及任何 DDL/DML。

【哪类不变 · 可据此直接排除自查】① 后端接口零变更：所有 API 路径、请求/响应结构、HTTP 恒 200 + body.code 约定、错误文案、权限点与校验规则逐字一致，本次没有新增或修改任何路由。② 数据库零变更：没有新增 Alembic 迁移（head 仍是 0019_basics），不建表、不加列、不删表，升级过程不 UPDATE 任何存量行。③ 金额与计价口径不变：报价单税额（按行税率合计、tax_rate 仅兜底）、工资核算、库存结存、盘点入账、返工成本等算法一行未改，不重算、不回填任何历史单据。④ 商业扩展包零变更：全部已安装扩展的 manifest.json / router.py / models.py / migrations.sql / frontend/plugin.js 一行未改，不需要重新打包上传开发者中心、不需要重装扩展、不需要重跑 migrations.sql。本次的兜底保护做在宿主侧，即使扩展仍保留 from app.models.xxx import <表对象> 的旧写法也不会再被误摘；但仍建议扩展改为只 import app.models 模块对象（qcode 2.1.7 已按此修正）。⑤ 前端零变更：v2.2.18 引入的扩展运行时桥（extensionBridge.ts，4 类桥 + 13 个 Element Plus 组件）原样保留，dist 由 CI 用同一份源码重建，扩展页面渲染行为与 v2.2.18 一致。⑥ 零扩展实例行为等价：没有装任何扩展时 purge 无对象可摘，升级前后完全一致。

【历史数据如何处理】无需处理，也不需要补录。本次没有数据迁移，也不存在「以为跑成功、实际没写入」的缺口需要人工补齐——worker 侧失败的任务是整体失败（无部分写入），不会留下半截记录。需要注意的一点：Celery 中此前已重试耗尽或已丢弃的旧消息不会被重放，升级只保证「从现在起」的周期投递能正常执行；若某条长期失败的自动化任务本该在此之前处理到期工单，请升级后到对应台账抽查一次是否有到期未推进的单据，按业务流程手工推进，不要期待系统自动追溯。

【升级后需要你做什么】① 重启后端（Web）进程，关于页与 system_versions 表才会同步到 v2.2.19；本仓 main.py 在启动时读取 CHANGELOG.json 写入版本表，只改文件不重启会继续显示 v2.2.18。② 重启 Worker 与 Beat，新 loader.py 与新的 worker_init 注册逻辑才会生效；若走后台在线升级，这一步由升级 Job 自动完成，无需手工干预。手工部署时请按既有规矩：后端 kill -TERM 后等宝塔自愈接管、不手动拉起；Worker/Beat 走宿主 worker_control 的信号通道或系统服务重启，不要用 setsid/nohup 起进程。③ 重启后抽查一次日志：连续观察两个 beat 周期（约 20 分钟），确认不再出现 Received unregistered task 与 failed to locate a name，且 automation.pipeline 有 succeeded 记录。④ 若你的实例此前一直没装扩展，这一步只需重启后端刷新版本号即可，其余无变化。

【条件性提示】若实例上装的是自定义扩展，且其 crud.py 里仍写着 from app.models.user import user_roles 这类「直接引入核心表对象」的语句，升级到 v2.2.19 后不会再触发本缺陷（宿主已加保护），但该写法本身仍属隐患，建议后续改成 import app.models 的形式；本次私有的 qcode 扩展已在其 2.1.7 版本完成该调整，与宿主此修复互不依赖、可分别升级。另需说明：本修复只解决「任务因 mapper 解析失败而无法执行」，不改变任何任务的业务逻辑与执行频率。

———— 以下为变更详情 ————

宿主 worker 扩展导入路径（backend/app/celery_app.py）：worker 此前同时注册 worker_init 与 worker_process_init 两个信号，两者都会调用 import_extension_modules()，而 prefork 模式下主进程与子进程各执行一次，等价于同一进程内二次导入。改为只保留 worker_init（主进程启动时导入一次，fork 出的子进程继承已注册的任务表）。这一处同时解决两个现象：主进程查不到 @shared_task 导致的 Received unregistered task，以及二次导入触发二次 purge 导致的表被误摘。

扩展表摘除边界（backend/app/extension_host/loader.py）：新增 _core_table_ids()，扫描 app.* 命名空间下已注册的 Table 对象并按对象 id 建立集合；_detach_extension_tables() 在按模块名认领表之前先做判断，命中核心表集合的直接跳过，绝不再从 Base.metadata 摘除。原实现仅按「表对象出现在哪个模块的命名空间」判断归属，这假设了核心表只会出现在 app.* 里，而扩展里一句 from-import 就能把同一个 Table 对象挂到扩展命名空间，属于前提不成立。

回归测试（backend/tests/test_extension_core_table_guard.py，新增）：3 个用例断言——扩展自有表在清理时被正常摘除、核心表 user_roles 在清理后仍留在 Base.metadata、Role.users 关系可正常解析。已做反向验证：临时移除核心表保护后该用例集失败，恢复后全部通过，确认它确实能抓到本缺陷而非空跑。

CI 稳定性（backend/tests/test_basics.py）：test_downtime_duration_computed_and_bounds 此前硬编码 2026-11-07 08:00 作为基线，UTC runner 上 datetime.now() 早于该时刻会算出负时长并断言失败，是纯粹的环境依赖缺陷，与业务逻辑无关。改为显式传入 ended_at，消除时区与执行时刻的耦合，宿主 CI 已由连续失败转为 success。
