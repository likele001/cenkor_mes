## 升级影响

- **不配任何东西也变快**：本版修掉了一个让升级后停机动辄十几分钟的真 bug。升级流程的守护脚本是从后端进程里派生的，会继承面板注入的进程身份标记，于是面板把它当成「项目主进程」——脚本等健康的整段时间里，面板一次都没把后端拉起来。升级到本版后，同一台服务器上「kill 到恢复」不再受这个因素拖累，最长也就是面板的一个巡检周期（宝塔默认 120 秒；实测从 11 分钟降到 100 秒出头）。
- **想让停机压到 10 秒内**：在服务器上配一项 `CENKORMES_START_CMD`（宝塔只需一条 sudo 白名单 + 一个 root 属主启动封装，配置步骤见 `docs/DEPLOYMENT.md` 8.5.1，五分钟能配完）。不配不影响任何功能，只影响升级时的停机时长，最长一个巡检周期。
- **数据零影响**：本版没有数据库迁移、没有表结构变更、没有接口契约变更、没有权限点增删。升级后不需要补数据，也不需要重配业务参数；v2.2.19 带进来的扩展加载修复继续有效。
- **升级后的自检**：如常访问「关于/版本」页，看到版本号变为 `v2.2.20` 即完成；`/api/health` 返回的 `version` 也应为 `v2.2.20`。

## 本次改动

**1）停机 11 分钟的真正原因（不是面板慢）**

2026-11-07 在本机做了完整在线升级实测（Job#15），时间线是：`19:13:29` 杀掉旧进程 → `19:13:31` 端口释放 → 直到 `19:24:41` 新进程才起来。此前一直以为是宝塔的守护周期（约 120 秒）造成的，实测证伪了：面板每一轮巡检都在跑，但每轮都判定「项目还在运行」，于是什么都不做。

面板判断项目是否在跑的依据不是 pidfile，而是扫 `/proc/<pid>/environ` 里有没有 `BT_PYTHON_SERVICE_SID=<项目 id>`。这个变量由项目的启动脚本 `export`，从后端进程继承下去的**任何**子进程都带着它——包括升级流程派生的那个守护脚本。于是脚本活着的那 600 秒里，面板把脚本当成了后端本身；脚本一退出，下一轮巡检（≤120 秒）立刻就把后端拉起来了。

修法：派生守护脚本时显式传一份去掉该变量的环境（`_guard_env()`）。注意在脚本里 `unset` 是无效的——`/proc/<pid>/environ` 反映的是进程初始环境块，必须在 exec 之前摘掉。

**2）新增 `CENKORMES_START_CMD`：杀完立刻把后端拉起来**

只修上面那条，停机时间等于一个巡检周期（宝塔默认 120 秒）。想更快就要主动拉起：配置 `CENKORMES_START_CMD` 后，守护脚本在释放端口之后立刻执行它。宝塔现场推荐调面板自己的启动入口（`ServiceManager.start_project()`），这样进程身份、日志、pidfile 都和手点「启动」一致，被拉起的进程仍是 `www`，升级流程拿不到任何额外权限。

这一步刻意不在应用里自己 `nohup uvicorn`：手起的进程会抢端口，面板自愈随后反复 `address already in use`，pidfile 也不再归面板管。

顺带修掉一个竞态：端口释放 ≠ 进程已退出（uvicorn 优雅退出时先关监听 socket，进程还会拖几百毫秒到几秒），而面板启动入口只判「旧 pid 是否存在」，旧进程还在就直接跳过——命令返回「启动指令已执行」，实际什么都没起来。本版在拉起前排「等旧 pid 确实退出」，并对拉起结果做最多 3 次重试（每次观察 10 秒端口）。

**3）部署参数可以写进 `backend/.env`**：`CENKORMES_RESTART_CMD` / `CENKORMES_START_CMD` / `CENKORMES_CELERY_UNITS` 现在既认进程环境变量，也认 `backend/.env`。原因是宝塔的项目 env 文件只是一行 `source backend/.env`，而 `.env` 里没写 `export`，那些值进不了后端进程的 environ（应用本身能读 `.env` 是靠 pydantic-settings）。现场把参数写进 `.env` 是最自然的做法，现在能生效了。

**4）文档**：`docs/DEPLOYMENT.md` 新增 8.5.1「把升级停机从两分钟压到十秒」，含封装脚本、sudo 白名单、`.env` 三件套；同时把 9.1 里描述 v2.2.5 行为的过时段落改成现状，避免运维按老文档排查。`docs/RELEASE_PROCESS.md` 的环境变量表同步。

**5）回归**：新增 5 组用例覆盖上述三点（身份标记必须被摘掉、拉起脚本落盘与执行顺序、未配置时保持老行为、`.env` 回退读取），并做了反向验证——把 `env=_guard_env()` 去掉后相应用例立即失败。`tests/test_upgrade_preflight_restart.py` 30 项全通过。
