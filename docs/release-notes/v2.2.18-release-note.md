【升级影响 · 本次为宿主核心前端框架缺陷修复，不含数据库迁移、不含后端接口变更、不含任何计算口径调整，已有单据数据与集成方式一律不变；唯一变化是带前端的扩展页面从空白恢复为正常渲染，升级前请知悉】本次相对 v2.2.17 只改动两个前端源码文件：新增 frontend-admin-pro/src/utils/extensionBridge.ts，并让 src/main.ts 在启动时调用 installExtensionBridge()。修复的是扩展机制从上线起就缺失的运行时桥：宿主此前只把 Vue 核心挂到 window.Vue、只提供 window.__registerExtension，而 44 个已安装扩展的 plugin.js 普遍依赖 window.__extRequest / __extHttp / __extToast 以及挂在 window.Vue 上的 Element Plus 组件。结果是插件里 h(el.ElTable, ...) 的组件全为 undefined、取数时「__extRequest is not a function」被 try/catch 吞掉，页面只剩插件内一句纯文本「共 0 条」。该文案是前端数组长度，不是数据库条数——实测合同数据、接口返回、菜单与路由注册均正常。对照「旧数据和旧集成在不做任何操作的情况下会不会得到不同结果」这条判据，结论是：不会。以下按「哪类会变 / 哪类不变 / 历史数据怎么办 / 需要你做什么」逐项说明。

【哪类会变】仅两类，且都属于「把本来就该有的行为修回来」：① 带前端的扩展页面由渲染空白（无搜索框、无按钮、无表头、显示共 0 条）恢复为正常渲染并展示真实数据；② 扩展脚本经 __extRequest 调用接口遇到业务失败（body.code 非 200）时，从「被静默吞掉、页面按空数组渲染」变为 Promise reject，由插件自带的错误处理给出提示。桥已兼容历史插件的三套返回约定（{ data } / axios 风格 .data.data / 直接取业务字段），现有扩展无需改代码。除此之外，宿主自身页面、后端行为、权限判定均无变化。

【哪类不变 · 可据此直接排除自查】① 后端零改动：本次没有 Python 文件变更，所有 API 路径、请求/响应结构、HTTP 状态码、权限点与校验规则逐字一致；② 数据库零改动：没有新增 Alembic 迁移（head 仍是 0019_basics），不建表、不加列、升级过程不 UPDATE 任何存量行；③ 已有单据金额与计算口径不变：报价单税额（按行税率合计、tax_rate 仅兜底）、工资、库存结存、盘点入账等算法一行未改，不重算、不回填任何历史数据；④ 商业扩展零改动：44 个扩展的 manifest.json / router.py / models.py / migrations.sql / frontend/plugin.js 一行未改，不需要重装扩展、不需要重新打包上传开发者中心、不需要重跑 migrations.sql；⑤ 权限模型不变：本次不新增也不调整任何权限点，内置角色与自建角色的授权数据不动。

【历史数据如何处理】无需处理。本次没有数据迁移，也没有「以为保存成功、实际没写入」之类的历史缺口需要补录。升级过程只覆盖源码与前端产物，不触碰业务表。

【升级后需要你做的两件事】① 浏览器强刷（Ctrl+F5）清掉旧 JS 缓存：v2.2.17 及更早的 dist 不含桥，滞留的旧入口会继续显示空白；本次 Release 产物内的 dist 由 CI 用带桥源码重新构建，升级后新入口自带桥。② 确认非超管角色有扩展查看权限：GET /api/admin/extensions/{key}/plugin.js 要求 ext.<key>.view 或 setting.manage，缺权限返回 403，页面同样会空白——这是既有的权限边界，不是本次修复的缺陷，请在后台「角色管理」按岗位授权。注意 PUT /api/admin/system/roles/{id}/permissions 是全量替换，须先读出该角色全量权限再合并回写。

【条件性提示 · 仅针对手动热修过前端的实例】若实例曾直接替换 frontend-admin-pro/dist 来临时恢复扩展页面，本次升级会把 dist 换成正式产物，效果一致且此后可随版本固化。反过来，若升级或重装时使用的是 v2.2.17 或更早的 Release 产物，dist 会被换回无桥版本，扩展页面会再次空白——请勿回退到 v2.2.17 及更早版本。自建插件若依赖 window.Vue 上的组件，现在可直接取用，无需自行挂载。

扩展运行时桥（frontend-admin-pro/src/utils/extensionBridge.ts，新增）：installExtensionBridge() 在 window 上提供 __extRequest / __extHttp / __extToast / __registerExtension 四类桥，把 ElButton、ElTable、ElTableColumn、ElInput、ElInputNumber、ElSelect、ElOption、ElDialog、ElForm、ElFormItem、ElRadioGroup、ElRadioButton、ElDatePicker 共 13 个 Element Plus 组件及 ElMessage、axios 挂到 window.Vue，供以普通 script 加载的插件脚本使用。请求桥自动注入 Bearer token、处理 VITE_API_BASE 前缀、兼容字符串/对象/FormData 请求体，并统一按 body.code 判定业务成败：成功返回可同时按 { data } / .data.data / 直取字段三种方式读取，业务失败必须 reject，不再静默返回空数据。宿主 src/main.ts 由原来的 window.Vue = Vue 改为调用 installExtensionBridge()，保留 registerExtension 注册语义不变。

归属说明：缺陷在宿主核心（开源主程序 likele001/cenkor_mes）的前端框架层，不在任何商业扩展。扩展包只有 6 类文件、不含宿主前端产物，浏览器里也没有全局 window.ElementPlus 可供插件自举组件，因此改扩展包无法修复；私有仓 likele001/mes-extensions 与开发者中心 app_submissions 本轮均不需要改动。

测试与验证：vue-tsc -b 类型检查通过；vite build 构建通过；构建产物中 4 个桥与 13 个组件字符串全部存在；真实浏览器契约验证 4 个桥均为 function、window.Vue.ElTable 已挂载、合同接口取到 CT11793987328743（1 条）、错误请求正确 reject、crm_suite 插件注册 11 个菜单与 11 条路由（含 /ext/crm_suite/contracts）。Release 产物由 CI 现跑 npm ci && npm run build 并把预构建 dist 复制进包，前端 dist 不入库也能随 tag 固化。
