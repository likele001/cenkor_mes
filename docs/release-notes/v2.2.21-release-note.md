## 升级影响

- **内置角色的手工授权不再被重启抹掉**：`admin / leader / qc / employee / customer` 这 5 个内置角色，此前只要在后台给它们授过扩展权限，服务**每次重启**都会被「默认权限预设」整段覆盖回去，且日志一个字都不打。本版起改为「只补不删」：只把预设里缺的补上，已有多授的一律保留。
- **已经被覆盖掉的权限不会自动回来**：本版只阻止继续丢，不回填历史。升级后如果内置角色上少权限，需要**再授一次**——这一次会生效并长期保留。本机现场已确认丢失的是内置 `qc` 与 `leader` 各 5 个 `ext.qcode.*`（权限数精确回落到预设的 14 / 22）。
- **自建角色完全不受影响**：`worker` / `qc_inspector` / `workshop_leader` 等自建角色从来不在预设名单里，本版改动对它们零行为变化，不需要重授。
- **数据与契约零影响**：没有数据库迁移、没有表结构变更、没有接口契约变更、没有权限点增删。升级后不需要补数据，也不需要重配业务参数；v2.2.20 的升级停机优化（实测 15 秒）继续有效。
- **升级后的自检**：「关于/版本」页应显示 `v2.2.21`，`/api/health` 返回的 `version` 也应为 `v2.2.21`。

## 本次改动

**1）问题现象**

2026-11-07 复查授权时发现：上一轮给内置 `qc`（id=3）、`leader`（id=2）补的 5 个 `ext.qcode.*`，写入记录里明确是 `written: true, verified: true`，但复查时全部消失——权限数精确回落到 `ROLE_PERMISSION_PRESETS` 的 **14 / 22**。同一时间，3 个自建角色（`qc_inspector` 23 / `production_manager` 27 / `workshop_leader` 21）一个都没掉。

这意味着「在后台给内置角色授了权，看起来成功了，重启后静默失效」，且前端没有任何提示，排查成本极高。

**2）根因**

`app/main.py` 里 `DB_AUTO_SEED=true`（默认开启）的分支，每次进程启动都会执行 `create_default_roles()`。旧实现对**已存在**的角色同样执行：

```python
role.permissions = [perms_by_code[c] for c in preset]
```

这是整段替换，不是合并。`DEFAULT_ROLES` 只包含 `admin / leader / qc / employee / customer`，所以：

- 内置角色 → 被打回预设，手工授的权限蒸发；
- 自建角色 → 不在名单里，`if code in existing: role = existing[code]` 之后没有命中预设，权限原样保留。

在事务内跑一遍播种再回滚来验证，实测 `admin` 会从 154 个权限点掉到 **74**（80 个 `ext.*` 全部消失）。`admin` 现在看起来没掉，是因为扩展同步（`extension_host/host.py`）在播种**之后**又把 `ext.*` 补回给了 admin —— 而 `qc` / `leader` 没有任何环节会补。

**3）修法**

已存在的角色**只补不删**：只把预设里当前缺的权限补进去，已有的额外权限原样保留；只有新建角色才按预设全量初始化。

这样既保留了产品需要的能力（新版本给内置角色新增默认权限时，升级后能自动落地），又不再覆盖运维的人工配置。

**4）回归测试**

新增 `backend/tests/test_rbac_seed_idempotent.py`，5 个用例覆盖：手工加的额外权限在播种后仍在、预设缺的权限会被补上、重复播种幂等、新建角色按预设初始化、自建角色不受影响。

反向验证有效：换回旧实现 **2 failed**，新实现 **5 passed**；全量 **798 passed**（原 793 + 新增 5）。
